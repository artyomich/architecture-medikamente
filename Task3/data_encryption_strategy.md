# Задание 3. Оценка Data Encryption at Rest и In Transit

## 1. Классификация данных

Для выбора адекватных мер защиты данные классифицируются по:

- **Типу** (персональные, медицинские и т.д.),
- **Уровню чувствительности**,
- **Состоянию** (at rest / in transit / in use),
- **Контексту использования** (операционный, аналитический, архивный).

| Категория данных | Примеры | Уровень чувствительности | Состояние | Контекст |
|------------------|--------|--------------------------|----------|---------|
| **Персональные данные (ПДн)** | ФИО, дата рождения, email, телефон, адрес | `CONFIDENTIAL` | at rest, in transit | OPERATIONAL |
| **Медицинская тайна (PHI)** | Диагнозы, назначения, история болезни, анализы | `CRITICAL` | at rest, in transit, in use | OPERATIONAL |
| **Финансовые данные** | Договоры, чеки, реквизиты, данные об оплате | `CONFIDENTIAL` | at rest, in transit | OPERATIONAL |
| **Внутренние данные** | Журналы записей, внутренние распоряжения | `INTERNAL` | at rest, in transit | OPERATIONAL |
| **Публичные данные** | Прайс-листы, графики работы | `PUBLIC` | at rest | PUBLIC |

> **Примечание**: Все данные с идентификаторами (ФИО, email, телефон) автоматически относятся к `CONFIDENTIAL` или `CRITICAL`. Обезличенные данные — только после валидированной анонимизации.

---

## 2. Обоснование необходимости защиты

| Категория | Правовое и бизнес-обоснование |
|----------|-------------------------------|
| **ПДн (CONFIDENTIAL)** | Требования ст. 19 ФЗ-152: обязанность применять технические меры защиты (шифрование, аутентификация, аудит). Несоблюдение → штрафы до 75 000 ₽, приостановка обработки. |
| **PHI (CRITICAL)** | ФЗ-323, ст. 13: медицинская тайна. Нарушение → уголовная ответственность (ст. 137 УК РФ), репутационные риски. |
| **Финансовые данные** | Требования 152-ФЗ + PCI DSS (если используются данные карт). Риск мошенничества, финансовые потери. |
| **Внутренние данные** | Могут быть использованы для реконструкции личности (например, комбинация записи + ФИО). Требуют минимальной защиты (доступ по ролям). |
| **Публичные данные** | Не содержат ПДн — не требуют шифрования, но подлежат контролю целостности. |

## 3. Инструменты защиты

### 3.1. Защита данных **at rest** (в состоянии покоя)

| Тип данных | Метод шифрования | Инструменты | Примечание |
|-----------|------------------|-------------|-----------|
| **PHI, CONFIDENTIAL** | Application-level encryption (AES-256) | PostgreSQL + `pgcrypto`, ClickHouse encrypted columns, HashiCorp Vault для управления ключами | Шифрование на уровне приложения, ключи — вне БД |
| **Файловое хранилище** | Server-Side Encryption (SSE) | MinIO с SSE-KMS, ключи в Yandex KMS или Vault | Полная прозрачность для приложений |
| **Файловый сервер / ОС** | Full Disk Encryption (FDE) | LUKS (Linux), BitLocker (Windows Server) | Защита от физического доступа |
| **Резервные копии** | Шифрование до архивации | Velero + restic с AES-256, GPG | Ключи хранятся отдельно от бэкапов |
| **Внутренние / Публичные** | Не шифруются | — | Доступ по ролям (RBAC) |

> ✅ **Требование**: Все ключи шифрования управляются централизованно (HashiCorp Vault, Yandex KMS). Никаких hardcoded-ключей.

---

### 3.2. Защита данных **in transit** (в процессе передачи)

| Канал | Протокол | Инструменты | Примечание |
|-------|--------|------------|-----------|
| **Внешний трафик** (пациент → портал) | TLS 1.3 | Nginx, Let's Encrypt, Certificate Pinning | Запрещены TLS 1.0–1.2 |
| **Интеграция с лабораторией** | HTTPS + mTLS | Istio, mutual TLS, JWT/OIDC | Двусторонняя аутентификация |
| **Межсервисное взаимодействие** | mTLS | Istio Service Mesh или Linkerd | Автоматическая выдача сертификатов |
| **Доступ к БД / очередям** | TLS 1.3 | PostgreSQL SSL, Kafka SSL | Ограничение по IP + сертификатам |
| **Резервное копирование** | TLS 1.3 + шифрование | MinIO → S3-compatible с TLS | Шифрование на прикладном уровне дополнительно |

> ✅ **Требование**: Все каналы — только по TLS 1.3 с сильными шифрами (`TLS_AES_256_GCM_SHA384`).

---

### 3.3. Дополнительные меры

| Мера | Инструменты | Применение |
|------|------------|-----------|
| **Аутентификация и авторизация** | Keycloak + RBAC/ABAC | Все пользователи и сервисы |
| **Маскирование и обфускация** | Dynamic Data Masking (PostgreSQL), Apache ShardingSphere | При отображении данных в UI и API |
| **Целостность данных** | SHA-256 хеши, подписи | При передаче файлов, бэкапов |
| **Аудит и логирование** | ELK Stack + Wazuh (SIEM) | Полнолуние логирование всех операций с `CONFIDENTIAL` и `CRITICAL` |
| **Хранение на территории РФ** | Yandex.Cloud, VK Cloud, Selectel | Обязательно для всех ПДн |

## 5. Итоговая таблица защиты

| Данные | В чём необходимость защиты | Инструменты защиты |
|--------|----------------------------|-------------------|
| **ФИО, email, телефон** | Риск идентификации, требование ФЗ-152 | AES-256 (at rest), TLS 1.3 (in transit), RBAC, динамическое маскирование |
| **Адрес, место работы** | Может быть использовано для профилирования | То же + запрет передачи в аналитику без согласия |
| **Медицинские карты, диагнозы** | Медицинская тайна (ФЗ-323), уголовная ответственность | Application-level AES-256, mTLS, ABAC, полный аудит, secure wipe |
| **Результаты анализов** | Чувствительные медицинские данные | То же + обезличивание для аналитики (k-anonymity) |
| **Договоры, чеки** | Финансовый риск, ФЗ-152 | AES-256, TDE, хранение в отдельной зоне, RBAC |
| **Журналы записей** | Метаданные, могут раскрыть факт обращения | AES-256, TLS 1.3, RBAC |
| **Прайс-листы, графики** | Публичная информация | Не шифруются, контроль целостности (хеши) |

---

Данная стратегия:
- **Полностью соответствует** требованиям ФЗ-152 и ФЗ-323.
- Учитывает **все состояния данных** (at rest, in transit, in use).
- Использует **только проверенные open-source и коммерческие инструменты**.
- Поддерживает **автоматизацию**, **аудит** и **масштабируемость**.
